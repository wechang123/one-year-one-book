### 10:14 ❗ AI가 자기가 어제 발견한 것을 다시 어겼다

**무엇이 문제였나**
스키마를 새로 쓰면서 `datasource db { url = env("DATABASE_URL") }`를 넣었다.
Prisma 7부터는 이게 금지다 — 연결 문자열은 `prisma.config.ts`가 맡는다.

**어떻게 발견했나**
Docker 빌드가 `npx prisma generate`에서 실패했다. 에러 코드 `P1012`.
로컬에서 재현하려 했더니 `node_modules`가 없어서 다른 에러가 났고, **컨테이너 빌드 로그를 직접 다시 잡아** 원인을 확인했다.
`grep`으로 "error"만 걸러서는 안 나왔다 — 빌드 로그는 실패 라인만 요약해서 보여주기 때문에 **해당 스텝의 전체 출력**을 봐야 했다.

**왜 일어났나 — 이게 핵심이다**
어제 **정확히 이 문제를 이미 겪었고**, 커밋 메시지에 이렇게까지 적어뒀다.

> *"Prisma 7은 스키마에 url을 둘 수 없다 — 연결 문자열은 prisma.config.ts가, 실제 연결은 어댑터가 맡는다."*

그런데 새 저장소에서 스키마를 **처음부터 다시 쓰면서** 그 기록을 참조하지 않고 관성대로 썼다.

**교훈**
검증된 설정을 옮길 때는 **다시 쓰지 말고 복사해야 한다.** 인프라 파일은 그대로 복사해서 문제가 없었고,
유일하게 손으로 새로 쓴 파일(`schema.prisma`)에서 사고가 났다.
"이 정도는 기억한다"가 가장 비싼 가정이다.

### 10:46 포트 충돌 — 남의 포트를 뺏지 않기로

`docker compose up -d db`가 *"Bind for 0.0.0.0:5433 failed"*로 죽었다.
범인은 **같은 머신에서 계속 돌고 있던 다른 프로젝트의 DB 컨테이너**였다. 10시간째 5433을 잡고 있었다.

그걸 내리는 대신 이쪽이 비켜갔다 — `.env`에 `DB_PORT=5434`.
**남이 쓰고 있는 포트를 뺏는 대신 이쪽이 옮길 수 있어야 한다**는 게 포트를 환경변수로 뺀 이유였고,
그 설계가 실제로 필요해진 첫 사례다. 요건인 *"포트 환경변수 변경"*을 문서가 아니라 사고로 검증했다.
(`.env`는 gitignore라 심사자는 기본값 5433·3000으로 그냥 돌아간다)

### 10:50 ❗ 로컬에서 `npm run seed`가 죽었다

*"DATABASE_URL이 없다"*. 컨테이너에서는 compose가 넣어주지만 **로컬 `tsx`는 `.env`를 안 읽는다.**

`dotenv`를 쓰지 않았다. 이 파일은 **프로덕션 컨테이너에서도 실행**되는데 거기서 개발 의존성에 기대고 싶지 않았다.
Node 20.6+의 `process.loadEnvFile()`을 `try/catch`로 감쌌다 — 의존성 0, `.env`가 없는 컨테이너에서도 정상.

### 10:53 주문 1건도 넣지 않기로 — 스키마가 답을 줬다

원래 계획은 *"주문 1건만 넣어 상태 표시를 보여준다"*였다. 스키마를 확정하고 보니 불가능했다.

`Order`는 `Collection`에 딸려 있고, 책은 `@@unique([profileId, year])`다.
→ **주문 1건을 넣으려면 2026년 책을 먼저 만들어야 한다.**
→ 그러면 **심사자가 만들어볼 책이 사라진다.** 눌러볼 게 없던 이전 프로젝트의 실패를 그대로 반복한다.

대신 도달 경로를 짧게 만든다: **책 만들기(버튼 1) → 주문(폼 1) → 상태 변경(버튼 1).**
심사자가 **직접 만든** 주문의 상태가 바뀌는 걸 보는 편이, 남이 만든 주문을 구경하는 것보다 강하다.

### 12:24 공개 전 정리 — 지운 커밋이 오히려 원문을 박제한다

공개로 돌리기 전에 히스토리를 훑었다. `git log --all -p`로 **13건**이 걸렸다.
제3자 회사 실명, 개인 이메일, 그리고 이 저장소 밖의 사정이 적힌 줄들이었다.

**핵심은 이거다** — 그중 상당수가 *"파일에서 지운 커밋"* 안에 있었다.
지우는 커밋의 diff가 삭제된 원문을 그대로 보여준다. **지우는 행위가 박제였다.**
추적 파일만 깨끗하면 된다고 생각했던 게 틀렸다.

`git filter-repo`로 재작성했다. 순서를 정한 근거 하나: **파일 정리를 먼저 커밋하고 재작성했다.**
반대로 하면 정리된 내용이 새 히스토리에 안 들어간다.

**설계가 바뀐 지점**: 처음엔 지정된 6개 문자열만 치환하려 했는데, 실제 줄을 보니
**한 단어를 지워도 같은 줄의 나머지가 문맥을 그대로 복원**했다.
문자열이 아니라 **줄 단위로** 지우는 방식으로 바꿨다.
조사 원자료(685줄)는 치환 대신 **히스토리에서 파일째** 뺐다 — 결론이 `03-feasibility.md`에
이미 다 들어가 있어서 두 벌을 유지할 이유가 없었고, 정본이 둘이면 갈라진다.

검증은 재작성 **후에** 다시 grep해서 0건을 확인했다. 시드 이미지 10장은 sha256을 재작성 전후로
대조했다 — 정규식이 바이너리를 건드리지 않았다는 확인이 필요했다.

**force push로는 안 끝난다.** 옛 커밋이 SHA URL로 계속 열린다.
아무도 보지 않은 Private 저장소였으므로 **원격을 지우고 다시 만들었다.**

### 13:09 ❗ 잰 적 없는 값을 "실측했다"고 쓸 뻔했다 — 두 번

**1) 도구가 성공을 반환했는데 실제로는 안 됐다**

브라우저 창을 `375×812`로 줄이는 호출이 **`Successfully resized`를 반환했다.**
그런데 페이지에서 `window.innerWidth`를 찍어보니 **500**이었다.
macOS Chrome이 최소 창 너비로 잘라낸 것이다. **375px에 도달할 방법이 아예 없었다.**

반환값만 믿었으면 *"375px에서 확인했다"*는 틀린 문장을 PR 4개에 전부 남길 뻔했다.

> 🔑 **도구의 성공 반환값은 결과가 아니라 주장이다.**
> 재려던 값을 재고 나서야 잰 것이다.

같은 origin의 **375px iframe**을 띄우고 그 안에서 `matchMedia('(min-width:700px)')`가
`false`인 것까지 확인하는 방식으로 바꿨다. iframe은 진짜 중첩 뷰포트라 미디어쿼리가 375로 평가된다.

**2) 어제 커밋 메시지에 같은 종류의 문장이 있었다**

목록 화면 커밋에 *"1440px에서 4열(카드 322px)임을 실측했다"*라고 써뒀는데,
그때 실제로 측정된 뷰포트는 **1512px**이었다. 리사이즈가 안 먹은 걸 모르고 쓴 것이다.

오늘 진짜 1440에서 다시 쟀다. **결과는 4열·322px로 같았다.**
`.page`의 `max-width`가 1400px이라 그 이상 폭에서는 배치가 동일하기 때문이다.

숫자는 맞고 **출처가 틀린 문장**이었다. 커밋 메시지를 고치려면 force push가 필요한데,
맞는 숫자를 고치자고 히스토리를 다시 흔들 이유가 없다고 봤다.
대신 여기 남긴다 — **정정을 정정으로 남기는 편이, 틀렸던 적이 없는 것처럼 만드는 것보다 낫다.**

### 13:22 ❗ `accept` 속성을 방어라고 부를 뻔했다

등록 폼에 `accept="image/jpeg,image/png,image/webp"`가 있으니 형식 검사는 됐다고 넘어갈 뻔했다.
그건 **갤러리에서 보이는 파일을 줄이는 안내**일 뿐이고, 서버 액션은 폼을 거치지 않고도 호출된다.

말로 넘기지 않고 **실제로 뚫었다.** 내용은 텍스트인데 `type`만 `image/jpeg`라고 주장하는
`File`을 폼에 밀어넣고 제출했다. 매직 넘버 검사가 없었으면 **통과했을 요청**이다.

그래서 형식을 `File.type`이 아니라 **바이트 앞부분에서 읽도록** 바꿨다(`lib/image.ts`).
이 값이 그대로 사진을 내려줄 때의 `Content-Type`이 되므로, 들어오는 자리에서 확정하지 않으면
나가는 자리에서 고칠 기회가 없다.

### 13:30 ❗ "빈 상태를 확인했다"를 코드만 읽고 쓸 뻔했다

시드 10점은 **전부 아이 말이 있어서** 빈 분기가 한 번도 렌더된 적이 없었다.
코드를 읽고 "되겠지"로 넘어갈 뻔했고, 대신 DB에서 한 건을 `NULL`로 만들어 **실제로 렌더시킨 뒤**
원문으로 되돌리고 `lib/seed-data.ts`와 문자열 대조해 복구까지 확인했다.

### 17:36 ❗ 크기 검사가 도달할 수 없는 코드였다 — 그리고 그걸 증명했다

`next.config.ts`의 `bodySizeLimit`과 `actions.ts`의 `MAX_BYTES`가 **둘 다 8MiB**였다.
그런데 앞의 것은 **파일이 아니라 요청 본문 전체**에 걸린다 —
multipart 경계, 필드 이름, 아이 말, 만든 날까지 포함이다.

그래서 8MiB를 넘는 파일은 **본문 단계에서 먼저 잘려 액션이 시작조차 못 했고**,
`"사진이 너무 큽니다"`는 **한 번도 실행된 적 없는 코드**였다.
화면은 `8MB까지`라고 안내하면서 **경계에서 거짓말**을 하고 있었다.

고치는 것보다 **고쳤다는 걸 증명하는 게** 어려웠다.
진짜 JPEG 헤더(`ff d8 ff`)로 시작하는 **8,936,491B** 파일을 만들어 제출했고,
그다음 **설정을 원래대로 되돌려 같은 파일을 다시 넣었다.**

| `bodySizeLimit` | 결과 |
|---|---|
| `"8mb"` (원래) | 한국어 문구 **0건** · 오류 경계로 떨어짐 |
| `"12mb"` (고친 뒤) | `사진이 너무 큽니다 (8.5MB). 8.0MB까지 올릴 수 있어요.` |

> 🔑 **되돌려서 재현하는 데 든 시간이 고치는 데 든 시간보다 길었다.**
> 그런데 그 실행이 없었으면 *"죽은 코드였다"*는 문장이 **추측**이었다.

덤으로 이 실행이 **실패 화면(`error.tsx`)의 필요성도 같이 증명했다** —
설정을 되돌린 상태의 요청이 정확히 그 화면으로 떨어졌다. 그게 없었으면 사용자는 빈 화면을 봤다.

### 17:38 ❗ [다시 시도] 버튼이 복구를 못 했다

### 19:05 ❗ "이미지가 안 뜬다"가 두 번 다 앱 문제가 아니었다

검증 중 **홈에서 이미지가 하나도 안 뜨는** 상황을 두 번 만났다. 둘 다 원인이 앱 밖이었다.

**② 배경 탭에서 `loading="lazy"`가 지연됐다.**
`fetch`로는 200이 오는데 `<img>`는 `complete: false`였다. `document.visibilityState`를 찍어보니 **`hidden`**.
`loading="eager"`로 바꾸니 즉시 `1194x1843`으로 로드됐다.

> 🔑 **"화면에 안 보인다"는 증상이지 원인이 아니다.**

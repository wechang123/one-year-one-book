### 10:00 문제 정의 · 사용자 정의
문서 두 개를 15분에 썼다(계획 80분). 다른 주제로 같은 고민을 이미 한 번 해봐서 빨랐다.

**설계에 영향을 준 판단 하나**: 이 서비스는 트리거가 앱 밖에 있다.
*아이가 그림을 들고 오는 것*이 트리거고, 그건 앱이 만들지 않아도 반드시 발생한다.
그래서 **주기·마감·알림 규칙을 아예 만들지 않기로 했다.** 앞선 시도의 최대 약점이 "사용자가 왜 다시 여는가"였는데, 여기서는 그 문제가 구조적으로 없다.

### 10:10 인프라 이식
Dockerfile · docker-compose · entrypoint · Prisma 연결을 직전에 검증해둔 것에서 그대로 옮겼다.
검증이 끝난 것을 다시 만들 이유가 없다. 이름만 치환.

**직접 내린 판단**: `next.config.ts`에 `serverActions.bodySizeLimit`을 8mb로 뒀다.
기본값이 1MB인데 폰으로 찍은 사진은 2~5MB다. 이 설정이 없으면 **업로드가 오류 없이 조용히 실패한다.**
이 서비스는 사진이 콘텐츠라 그 실패가 곧 서비스 전체의 실패다.

### 10:14 ❗ AI가 자기가 어제 발견한 것을 다시 어겼다

**무엇이 문제였나**
스키마를 새로 쓰면서 `datasource db { url = env("DATABASE_URL") }`를 넣었다.
Prisma 7부터는 이게 금지다 — 연결 문자열은 `prisma.config.ts`가 맡는다.

**어떻게 발견했나**
Docker 빌드가 `npx prisma generate`에서 실패했다. 에러 코드 `P1012`.
로컬에서 재현하려 했더니 `node_modules`가 없어서 다른 에러가 났고, **컨테이너 빌드 로그를 직접 다시 잡아** 원인을 확인했다.
`grep`으로 "error"만 걸러서는 안 나왔다 — 빌드 로그는 실패 라인만 요약해서 보여주기 때문에 **해당 스텝의 전체 출력**을 봐야 했다.

**왜 일어났나 — 이게 핵심이다**
어제 **정확히 이 문제를 이미 겪었고**, 커밋 메시지에 이렇게까지 적어뒀다.

> *"Prisma 7은 스키마에 url을 둘 수 없다 — 연결 문자열은 prisma.config.ts가, 실제 연결은 어댑터가 맡는다."*

그런데 새 저장소에서 스키마를 **처음부터 다시 쓰면서** 그 기록을 참조하지 않고 관성대로 썼다.

**교훈**
검증된 설정을 옮길 때는 **다시 쓰지 말고 복사해야 한다.** 인프라 파일은 그대로 복사해서 문제가 없었고,
유일하게 손으로 새로 쓴 파일(`schema.prisma`)에서 사고가 났다.
"이 정도는 기억한다"가 가장 비싼 가정이다.

**시간 손실**: 약 8분

### 10:43 ❗ 시드 문장 12개를 전량 폐기했다

**무엇이 문제였나**
어제 쓴 12문장은 **그림을 확보하기 전에** 썼다. *"코 고는 소리도 그렸는데 안 보여?"* 같은 문장이었다.
그런데 실제로 확보한 CC0 그림은 **수탉·자동차·건물·스페인어 만화**였다. **하나도 안 맞았다.**

**왜 일어났나**
"이미지 확보는 라이선스 조사에 달렸으니, 독립적인 문장 설계를 먼저 하자"고 판단했다.
효율적으로 보였지만 **제품의 순서를 거스른 설계**였다.

> 🔑 부모는 말을 정해두고 그림을 찾지 않는다. **그림을 받고 나서 아이에게 묻는다.**
> 문장을 먼저 쓴 것은 이 서비스가 실제로 쓰이는 순서와 반대였다.

**어떻게 고쳤나**
`public/seed/` 10장을 **한 장씩 실제로 열어보고** 그 그림에 맞는 말을 다시 썼다.
12점 → 10점으로 줄었다. **숫자를 맞추려고 문장을 지어내지 않았다.**

건진 것: 그림을 보고 쓰니 *"그림만 보면 절대 모를 것"*이 목표 3개를 넘어 **7개** 나왔다.
톱니 이빨이 **웃는 것**이고, 얼굴을 가로지른 선이 **이불**이고, 몸통이 없는 건 **옷 때문에 안 보여서**다.
그림 없이 상상해서는 이런 문장이 안 나온다.

**시간 손실**: 어제 문장 작성분 전량. 다시 쓰는 데 약 12분

### 10:46 포트 충돌 — 남의 포트를 뺏지 않기로

`docker compose up -d db`가 *"Bind for 0.0.0.0:5433 failed"*로 죽었다.
범인은 **같은 머신에서 계속 돌고 있던 다른 프로젝트의 DB 컨테이너**였다. 10시간째 5433을 잡고 있었다.

그걸 내리는 대신 이쪽이 비켜갔다 — `.env`에 `DB_PORT=5434`.
**남이 쓰고 있는 포트를 뺏는 대신 이쪽이 옮길 수 있어야 한다**는 게 포트를 환경변수로 뺀 이유였고,
그 설계가 실제로 필요해진 첫 사례다. 요건인 *"포트 환경변수 변경"*을 문서가 아니라 사고로 검증했다.
(`.env`는 gitignore라 심사자는 기본값 5433·3000으로 그냥 돌아간다)

### 10:47 스키마 — 넣지 않기로 한 것들이 판단이다

커밋을 3개로 쪼갰다. 결정 하나에 마이그레이션 하나.

| 안 넣은 것 | 왜 |
|---|---|
| `Artwork.collectionId` | 어느 책에 들어가는지는 이미 `madeOn` 연도가 정한다. 외래키를 따로 두면 *"2026년에 만들었는데 2025년 책에 담긴 작품"* 같은 모순이 만들어질 수 있다. **없는 필드는 틀릴 수 없다** |
| 사진 바이트를 `Artwork`에 | 목록 화면은 바이트가 필요 없다. 같은 테이블에 두면 목록 쿼리가 매번 수 MB를 끌고 온다. `select`로 막을 수는 있지만 **"실수하면 조용히 느려지는" 구조는 만들지 않는다** |
| 주문 가격·쪽수·배송일 | 제작 사양이 안 정해졌다. 지어내면 화면은 채워지지만 근거가 없다 |
| 배송완료 상태 | 요구가 3단계다. 넷째 단계는 배송사 연동 없이 *누가 언제 바꾸는지* 설명할 수 없다 |

넣은 것 중 설명이 필요한 것: `Order.status`와 `OrderEvent`를 **둘 다** 뒀다.
목록은 조인 없이 현재 상태를 읽어야 하고, 상세는 *"언제부터 그 상태였나"*를 보여줘야 한다.
현재 상태만 덮어쓰면 뒤쪽 답이 사라진다.

### 10:50 ❗ 로컬에서 `npm run seed`가 죽었다

*"DATABASE_URL이 없다"*. 컨테이너에서는 compose가 넣어주지만 **로컬 `tsx`는 `.env`를 안 읽는다.**

`dotenv`를 쓰지 않았다. 이 파일은 **프로덕션 컨테이너에서도 실행**되는데 거기서 개발 의존성에 기대고 싶지 않았다.
Node 20.6+의 `process.loadEnvFile()`을 `try/catch`로 감쌌다 — 의존성 0, `.env`가 없는 컨테이너에서도 정상.

### 10:53 주문 1건도 넣지 않기로 — 스키마가 답을 줬다

원래 계획은 *"주문 1건만 넣어 상태 표시를 보여준다"*였다. 스키마를 확정하고 보니 불가능했다.

`Order`는 `Collection`에 딸려 있고, 책은 `@@unique([profileId, year])`다.
→ **주문 1건을 넣으려면 2026년 책을 먼저 만들어야 한다.**
→ 그러면 **심사자가 만들어볼 책이 사라진다.** 눌러볼 게 없던 이전 프로젝트의 실패를 그대로 반복한다.

대신 도달 경로를 짧게 만든다: **책 만들기(버튼 1) → 주문(폼 1) → 상태 변경(버튼 1).**
심사자가 **직접 만든** 주문의 상태가 바뀌는 걸 보는 편이, 남이 만든 주문을 구경하는 것보다 강하다.

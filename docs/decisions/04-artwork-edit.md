# 04. 설명 편집 — 사진을 안 바꾸는 것이 기능 제외가 아니라 전제다

> 이슈 #4 · `app/artwork/[id]/edit/`

## 왜

등록은 아이가 그림을 내미는 **30초** 안에 끝나야 해서 아이 말을 **비운 채로도 저장된다**.
그런데 나중에 물어본 말을 채워 넣을 방법이 없었다. 만든 날 오타도 못 고쳤다.

## 판단

**고칠 수 있는 것은 `childQuote`와 `madeOn` 둘뿐이다.**
이 둘이 **실제로 나중에 바뀌는 값**이다. 사진은 아니다.
잘못 고른 사진은 **등록 화면의 미리보기**에서 잡는다([03](./03-artwork-new.md)) — 그게 미리보기를 넣은 이유였다.

### 🔑 사진 교체를 넣지 않은 것은 기능을 뺀 게 아니라, 이미 있는 두 코드를 성립시키는 전제다

| 이 전제 위에 서 있는 것 | 교체를 열면 무슨 일이 나나 |
|---|---|
| `api/photo/[artworkId]/route.ts`의 `Cache-Control: immutable` | `immutable`은 *"이 주소의 바이트는 영원히 안 바뀐다"*는 약속이라 **ETag·Last-Modified 없이도 성립한다.** 교체가 가능해지면 그 약속이 거짓이 되고, 브라우저는 **1년 동안 옛 사진을 보여주면서 재확인할 방법조차 없다** |
| `lib/seed-data.ts`의 `photo.upsert.update`에 `bytes`가 없는 것 | 지금은 `Photo.bytes`를 덮어쓰는 코드 경로가 **어디에도 없다**(등록은 항상 새 `Photo`를 만든다). 교체를 열면 시드 사진이 사용자 사진으로 바뀐 뒤 재시드해도 `mimeType`·`width`·`height`만 되돌아오고 **바이트는 안 돌아온다** |

그래서 `route.ts`의 헤더 옆에 이 전제를 **코드에 명시**했다 —
*"교체를 넣으려면 이 헤더를 먼저 바꿔야 한다."*
나중에 이 헤더를 보는 사람이 왜 ETag가 없는지 묻지 않아도 되게.

**진입 버튼 문구를 아이 말 유무로 나눴다.**
말이 있으면 `설명 고치기`, 비어 있으면 `아이 말 채우기`.
비어 있을 때 할 일은 *고치는 것*이 아니라 **지금 물어보고 채우는 것**이다.
같은 버튼이라도 무엇을 하러 가는지가 다르면 그렇게 말해야 한다.

**만든 날 도움말이 숨은 결과를 미리 말한다** — `연도를 바꾸면 담기는 책이 바뀝니다`.
수록작은 `madeOn`의 연도로 계산한다(`schema.prisma`의 `Collection`, 외래키가 없다).
화면이 말하지 않으면 나중에 책을 만들 때 **왜 이 작품이 빠졌는지 알 방법이 없다.**

**저장 후 `?saved=1` 배너를 띄우지 않는다.**
그 문구는 `이제 원본은 정리하셔도 됩니다`인데, 편집 시점엔 원본을 이미 정리한 뒤다.
**맞지 않는 말을 재사용하지 않는다.** 대신 고친 결과가 보이는 상세로 돌려보낸다.

### 의도적으로 넣지 않은 것

| 안 넣은 것 | 이유 |
|---|---|
| **사진 교체** | 위 표가 이유 전부다. 넣으려면 `immutable` 헤더와 `seed-data.ts`를 같이 고쳐야 한다 |
| 삭제 | [02](./02-artwork-detail.md)에서 같은 판단을 했다. 되돌릴 수 없는 버튼은 [데모 초기화]와 역할이 겹치고 성격이 다르다 |
| 편집 이력 | `OrderEvent`처럼 이력이 필요한 건 **남이 바꾸는 값**이다. 아이 말은 본인이 고치고 이전 값을 볼 이유가 없다 |
| 자동 저장 | 아이 말은 한 글자가 뜻을 바꾼다. 고치다 만 문장이 저장되면 안 된다 |

## AI를 어떻게 다뤘나

**채택**: [03](./03-artwork-new.md)의 `useActionState` + `useFormStatus` 구조, 날짜 검증 규칙.
검증을 등록과 **같게** 유지했다 — 편집만 느슨하면 편집으로 우회해 미래 날짜를 넣을 수 있다.

**거부·수정 1 — `findUnique`로 존재 확인 후 `update` 하려던 것을 지웠다.**
자연스러워 보였지만 확인과 수정 **사이에** 지워질 수 있고, 그러면 같은 오류를 두 곳에서 처리하게 된다.
`update` 한 번이 답을 다 준다(없으면 예외).

**거부·수정 2 — 전제 검증을 남의 말로 받아들이지 않았다.**
*"사진 교체를 빼면 `seed-data.ts`의 `bytes` 누락 결함이 소멸한다"*는 주장을 그대로 쓰지 않고
`Photo.bytes`에 쓰는 코드 경로를 전부 찾아봤다. 등록은 **항상 새 `Photo`를 만들고**
기존 것을 갱신하지 않으므로, 교체가 없으면 바이트는 시드 시점에 한 번만 쓰인다.
**주장이 맞았고**, 그래서 근거를 코드 주석에 적을 수 있었다.

**거부·수정 3 — `textarea`를 제어 컴포넌트로 만들려다 되돌렸다.**
`value` + `useState`가 기본안이었는데, 이 폼은 **제출할 때 한 번만** 값을 읽는다.
글자마다 리렌더할 이유가 없어 `defaultValue`로 바꿨다.
